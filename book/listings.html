Chapter 3

Listing Websites

Listing websites are one of the most common and useful scraping targets. Real estate, jobs, products, cars, accommodation, classifieds, and many other websites follow a surprisingly similar structure: a collection of items is presented as a list, and each item links to a separate page containing more detailed information.

Once you recognize this structure, scraping a listing website becomes much easier to reason about. Instead of thinking about the website as one large page, we can divide the problem into a few distinct steps: find the listing pages, extract the individual item URLs, follow those URLs, extract the details, and continue until all available listings have been processed.

The Listing Structure

A typical listing website has two important types of pages. The first is a listing page, which contains multiple items. The second is an individual listing page, which contains the complete information about one item.

For example, a real estate website might show twenty apartments on a search results page. Each property card contains a title, price, location, image, and a link to the property's individual page. The individual page can then contain dozens of additional fields such as the number of rooms, floor, area, description, amenities, agent information, and property history.

This gives us a natural scraping flow:

  1. Start from a search or category URL.
  2. Extract the links to individual listings.
  3. Visit each listing page.
  4. Extract the required fields.
  5. Move to the next listing page.
  6. Repeat until all pages have been processed.

A Template I Used for Years

The following scraper is a simplified version of a template I used for years when working with real estate websites. I used variations of this structure to write and maintain numerous property listing scrapers.

For one client, I worked with this approach for around three years. For another client, I continued working with it for around four years. Both clients were machine learning engineers working on real estate research projects. They needed enormous amounts of property data to build datasets and train their models, which meant that reliability and maintainability were often more important than making a scraper work once.

The template is deliberately straightforward. It separates the process of discovering property URLs from the process of extracting information from an individual property page.

                'current_page': current_page

            url = 'N/A'

Start With the Listing Page

The first thing I normally look for is the page containing the collection of listings. This is the page that gives the scraper its starting point.

In the template, that starting point is represented by base_url. It could be a search URL, a category URL, a location URL, or any other URL that produces a collection of properties.

The start_requests() method then creates the initial request and passes it to parse_links(). This creates a clean separation between starting the scraper and processing the listing page.

Extract the Individual URLs

Once the listing page has been loaded, the next question is simple: where are the links to the individual items?

In the template, this is represented by:

links = response.css('a[data-cy="propertyUrl"]::attr(href)').getall()

The selector itself is only a placeholder, because every website has its own HTML structure. The important part is the idea. We are not trying to extract every piece of information from the search results page. We are first interested in finding the URLs that lead to the actual listings.

This distinction is useful because listing pages and detail pages usually serve different purposes. The listing page tells us what exists, while the individual page tells us what each item contains.

Follow the Listing

Once the URLs have been collected, each one can be passed to parse_listing().

yield response.follow(
    url=card_url,
    headers=self.headers,
    meta={ 'filename': filename },
    callback=self.parse_listing
)

The detail parser can then concentrate entirely on extracting the fields belonging to one property. In a real scraper, the features dictionary might contain dozens of fields rather than just the URL.

features = {
    'url': url,
    'title': ...,
    'price': ...,
    'address': ...,
    'bedrooms': ...,
    'bathrooms': ...,
    'area': ...,
    'description': ...
}

Keeping this logic separate makes the scraper much easier to understand and maintain. If the website changes its property page layout, the detail parser can be updated without having to redesign the entire crawling process.

Then Deal With Pagination

Finding the listings on the first page is only part of the job. A real estate website may contain thousands or millions of properties distributed across many result pages.

The template therefore keeps a current_page value and determines the total number of pages before constructing the next URL.

The exact pagination mechanism varies from website to website. Some use URLs such as ?page=2, others use path-based URLs, offset parameters, cursor parameters, or completely different mechanisms. The scraper should first understand how the website moves from one batch of listings to the next and then reproduce that mechanism.

Debug Locally Before Crawling

One detail in this template became particularly useful during development: the DEBUG mode.

Instead of repeatedly downloading a live page while developing selectors, the scraper can load a previously saved copy of the HTML:

if DEBUG:
    with open('links.html') as f:
        response = Selector(text=f.read())

The same idea is used for an individual property page. This makes selector development much faster and avoids repeatedly requesting the website just to test a small change in the extraction code.

For long-running scrapers, this separation between development and production is extremely useful. The scraper can be tested against stable local HTML until the extraction logic works, and only then switched back to live requests.

Think in Two Separate Problems

When approaching a listing website, I find it useful to divide the problem into two independent questions.

  1. How do I discover every listing?
  2. How do I extract all the data from each listing?

The first problem is about navigation: entry points, categories, filters, pagination, infinite scrolling, and listing URLs. The second problem is about extraction: identifying the fields, locating their values, cleaning them, and storing them.

Keeping these problems separate is one of the main ideas behind the template above. Once the structure of a website is understood, the same basic architecture can be adapted to many different listing sites.

From One Website to Many

The reason this template became valuable over the years was not because it was particularly sophisticated. It was because it provided a repeatable structure for solving many similar problems.

Real estate websites may look completely different from one another, but underneath the visual differences they often have the same fundamental structure: search results contain property links, property pages contain fields, and some form of navigation connects the result pages together.

Once you start looking at websites in terms of these underlying structures rather than their visual appearance, scraping becomes much more systematic.

That way of thinking will be important throughout this book. The goal is not to memorize selectors or techniques for individual websites. It is to learn how to inspect a website, identify how its data is organized, and choose an appropriate way to extract it.

A Model to Remember

Keep this structure in mind throughout the book. Separating listing discovery from individual listing extraction is an important mental model that will help explain many of the design decisions we make later. We will return to this model repeatedly as we move from traditional scraping toward browser-based scraping.
